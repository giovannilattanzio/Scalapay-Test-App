## 8. Defect found by running the app

- [x] 8.1 [infrastructure] Set `baseUrl: CatalogApi.basePath` on the shared `Dio` in `_registerCore`. Without it every search fails before leaving the device: the generated `CatalogApi` applies `basePath` only when it builds its own client, so an injected `Dio` keeps an empty `baseUrl` and requests go out as the bare path `/v1/products/search`, surfacing as the error screen with no call made. Verify with a regression test that drives the REAL dependency graph — not a mocked `ProductsApi` — records the `RequestOptions.uri` a search produces through a fake `HttpClientAdapter`, and asserts it is absolute and starts with `CatalogApi.basePath`. The existing DI tests asserted the shared instance and its timeouts but never that a request resolves to a reachable URL, which is exactly why this reached a running app
- [x] 8.2 [design-system] Add the bottom system inset to `BottomSheetFrame` so every sheet organism keeps its last row clear of the home indicator. Measured on a 393x852 screen with a 34px indicator: the filters sheet's "Mostra risultati" button ends at 835 against a safe bottom of 818, **17px under the gesture bar**, and the sort sheet's last option clears it by only 4px. The cause is that `showModalBottomSheet(useSafeArea: true)` protects the top and sides only — the sheet always reaches the physical bottom. Fix it once in the shared frame, not in each sheet. Verify with widget tests that simulate a bottom inset and assert the last row ends above it, and that with no inset the layout is unchanged; the existing goldens must stay byte-identical, since `viewPadding` is zero in tests and Widgetbook (spec `design-organisms` — Bottom sheet frame)
